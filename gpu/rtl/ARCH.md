# Ядро ПЛИС «бомж-3D»: устройство и порядок работ (23.11.2026)

Ядро — отдельный битстрим Tang Nano 20K (слот ядер, грузит BL616 из кэша, как внешние ядра VDAC4).
Своё в нём только растеризатор; такты, SDRAM, HDMI и LINK берутся из FT-ядра VDAC4
(`fpga/vdac2/rtl`, версия 1.45 в слоте 1 — на плате с 31.10, «Чисто»).

## Что уже есть

| Часть | Где | Состояние |
|---|---|---|
| Договор команд и арифметики | `gpu/SPEC.md` | 0.2 |
| C-модель | `gpu/model/bomzh.c` | на демо Quake 2 совпадает с ref_soft до ±1 строки света (`results/bz`) |
| Этап A RTL: функциональное ядро | `gpu/rtl/bz_core.sv`, `bz_div.sv` | бит в бит с моделью (стенд `gpu/rtl/tb`) |

Этап A — автомат «точка за ~25 тактов» с простым портом памяти. Он нужен как образец: каждое
следующее изменение ядра гоняется на трассе Quake 2 и сравнивается с моделью по всей памяти.

## Такты и память (как FT-ядро 1.45)

- `fb_pll_sd`: вторая rPLL от кварца 27 МГц — clk_sd 121,5 МГц (контроллер SDRAM), clk_mem
  60,75 МГц (CLKOUTD ÷2, конвейер), CLKOUTP — клок микросхемы SDRAM со сдвигом PSDA.
- `sdram_burst` + `sdram_train`: пачки по 8 слов (32 байта), запрос до 8 пачек в строке, выборка DQ
  регистром у вывода, после включения подбор фазы и такта чтения (на плате FT 1.45: SD_TRAIN 0024189D).
- `sd_bridge`: клиенты на clk_mem → контроллер на clk_sd.
- PLL1 — только HDMI (пиксельный и ×5).

Пачка 32 байта = ровно кусок z из 16 точек; кусок цвета 16 байт — полпачки с маской DQM; строка
кэша текстур 64 байта — две пачки одним запросом.

## Вывод

424×240 (16:9, Hor+) ×3 → 1272×720 в кадре 1280×720p60 (по 4 точки чёрного слева и справа).
Строка кадра читается из SDRAM один раз в буфер строки (BSRAM), выдаётся три раза; точка — трижды.
Палитра 256×RGB (BSRAM) и вспышка FRAME — на выводе. hdmi_tx/tmds — из FT-ядра, TMDS DRIVE=4.
Смена кадров — на гашении после FRAME (двойной буфер).

Оценка по модели на демо (424×240, `tools/bz_summary.py`): SDRAM 121,5 МГц занята на 23 % в среднем,
31 % в худшем 1 % кадров (с выводом HDMI); на 60,75 МГц было бы 62 %.

|---|---|---|

| грани мира (lightmap) | 14,1 | 246 |
| TEX | 13,1 | 1119 |

Ужатие по порядку выгоды:

1. **Модели полосами, треугольник ставит ПЛИС** (−40,9 КБ): вершина (xy, zi, s|t, свет) идёт один раз,
   полоса/веер md2 (glcmds) — ~1 новая вершина на треугольник; плоскость треугольника (C, A, B для
   zi, s, t, l) считает ПЛИС: определитель, одно обратное (делитель уже есть), 8 умножений — ~50 тактов
   на треугольник, ~860 треугольников — 43 тыс. тактов на кадр (0,7 мс). Определяется в SPEC бит в бит.
2. **TEX и LMAP только при смене** (−11,4 КБ): передний край сейчас шлёт TEX перед каждым треугольником.
3. **LMAP в 2 слова, градиенты A/B мира по 16 бит с общим порядком, частица в 2 слова** (−7 КБ).

**Сделано 23.11 (SPEC 0.3):** TEX только при смене (90,5 → 79,1 КБ) и модели пачками VBUF/STBUF/TRIS с
постановкой треугольника в ПЛИС (→ 48,5 КБ на кадр, p99 86 КБ, это 2,6 МБ/с при 30 к/с; кадр против
ref_soft — тот же: 11,5 % индексов, 0,66 % заметно). Модели теперь 24 КБ вместо 53,6: вершин уходит
~1 на треугольник (видимая половина модели делит вершины хуже, чем вся), 3 слова на вершину. Дальше
по выгоде: градиенты мира по 16 бит (−3 КБ), LMAP в 2 слова (−3 КБ), вершина в 2 слова (−3,5 КБ),
частица в 2 слова (−1 КБ).

Оценка до ужатия была: остаётся ~31 КБ на кадр — ~1 МБ/с при 30 к/с (DOOM сейчас грузит по LINK ~1,3 МБ/с словами; потоковый
режим DMA ESP → окно FIFO даёт больше). Загрузки текстур — не по LINK, а вторым каналом (ниже).

## Второй вход: SPI Evo (28 МГц)

Выводы FT812 (`ft_sck`, `ft_cs_n`, `ft_mosi`, `ft_miso` через U6/U8 при M_SEL = 1) — SPI Z-контроллера
Evo. В ядре Quake 2 это канал загрузок: Z80 читает pak со своей карты и отдаёт текстуры, шкурки, небо,
картинки прямо в SDRAM Tang (заголовок «адрес SDRAM, длина» + данные; запись пачками через
sd_bridge). Карта уровня — 3,1–4,4 МБ текстур: ~1,5 с при ~3 МБ/с. ESP решает, что грузить, и
говорит Z80 через обычный обмен ESP↔Z80 (короткие события ≤63 байт). LINK остаётся под команды кадра.
Проверить: DMA TS-Config «RAM → SPI» (иначе Z80 OUT-ами, ~1 МБ/с).

## Возврат в слот 0 по сбросу Evo

Как у FT-ядра: плагин Z80 держит **M_SEL = 1**, пока идёт Quake 2. При сбросе Evo TS-Config сбрасывает
M_SEL в 0 — ядро ждёт 0,5 с (M_SEL = 0 и нет обмена по SPI Evo) и просит перезагрузку; BIOS Evo при
сбросе шлёт по SPI FT812 команду CORERST (68 00 00) — это сразу признак сброса. Перезагрузку делает
BL616 (бит в состоянии, которое он опрашивает, — как `next_cp` у ядра Next), плюс регистр LINK BOOT
(0xF0, «BOOT») для ESP. Без живой ESP ядро возвращается само.

## Вывод: масштаб 100 / 95 / 90 %

Своей настройки нет (слово пользователя 23.11): размер всегда как в слоте 0 — TS-Config CTRL (LINK 0x40,
биты 16:15), Q2.ELF читает его до запуска ядра и пишет ядру (регистр LINK), как ядро NES 0.9+.
Окно по центру 1280×720:
100 % — 1272×720 (×3 точно), 95 % — 1208×684, 90 % — 1145×648; не целое — ближайшая точка по DDA.
Выводы TMDS — **DRIVE=4** (как у всех ядер VDAC4 с 31.10: с DRIVE=8 экран терял сигнал).

## Этап B: конвейер 1 точка за такт (clk_mem)

```
LINK → FIFO команд (BSRAM) → разбор → [POLY] верх/низ, две цепочки рёбер (DDA, делитель на начало ребра)
  → FIFO отрезков (y, xl, xr) → нарезка по колонкам 16 → [перспектива] деление 2^46/zi на конец куска
  (radix-4, 16 тактов, конец куска = начало следующего) + умножение su·w → FIFO кусков
  → блок z: пачка z куска (32 байта) в буфер, сравнение по точкам → маска
  → точки: s, t шагом, волна, адрес плитки, кэш текстур 8 КБ (2 пути, строка 64 байта, BSRAM),
    lightmap (кэш клеток), билинейный свет, colormap (BSRAM), прозрачность (alphamap через кэш)
  → запись куска цвета (16 байт, маска) и z (32 байта, маска)
```

- Нагрузка по модели: точек растеризатора p99 308 тыс. на кадр 424×240 — 5 мс при 1 точке за такт
  на 60,75 МГц из 33 мс кадра 30 к/с. Делений ~ кусков + отрезков (~30 тыс. на кадр): один делитель
  radix-4 — 8 мс, поэтому делителей два или конвейерный.
- Арбитр SDRAM: вывод HDMI > z/цвет > промахи текстур > загрузки WRITE.

## Порядок работ

1. Оболочка: верхний модуль с fb_pll_sd, sdram_burst/train, sd_bridge, выводом 1272×720 из SDRAM,
   LINK (приём потока команд), этап A через переходник «слово ↔ пачка» с маленьким кэшем. Сборка
   Gowin: ресурсы и тайминг. Это уже рабочее (медленное) ядро.
2. Этап B — конвейер внутри той же оболочки, проверка на трассе против модели.
3. Поток LINK: ~155 КБ команд на кадр (p99) = 5 МБ/с при 30 к/с; DOOM сейчас грузит ~1,3 МБ/с.
   Нужен потоковый режим LINK (DMA ESP) и/или сжатие команд (ссылки на TEX/LMAP вместо повторов,
   короткие градиенты). Меряется на плате только по слову пользователя.

## Этап B: модули (план, 23.11.2026)

Каждая ступень — свой модуль; между ступенями — очереди (FIFO) с готовностью (valid/ready), чтобы
медленная ступень (промах кэша текстур, деление) не ломала соседние, а только задерживала их.

| Модуль | Что делает | Ресурсы (оценка) |
|---|---|---|
| bz_cmd | разбор команд, регистры TEX/LMAP/SCISSOR/TIME, SETUP (colormap, волна — в BSRAM) | ~600 LUT |
| bz_tri | TRIS: буферы вершин и st (BSRAM 512), постановка треугольника (делитель radix-4, умножитель) | ~900 LUT, 4 BSRAM, 2 DSP |
| bz_edge | многоугольник: верх/низ, две цепочки, край ребра — DDA (деление только в начале ребра) → FIFO отрезков (y, xl, xr) | ~800 LUT, 1 DSP |
| bz_span | отрезок → куски по колонкам 16; перспектива на концах куска: 2 делителя radix-4 (кусок = 16 тактов) + умножитель su·w; шаг через R[n] → FIFO кусков | ~1500 LUT, 4 DSP |
| bz_zbuf | кусок z: пачка 32 байта из SDRAM в буфер, сравнение 16 точек → маска; запись z пачкой с DQM | ~800 LUT, 1 BSRAM |
| bz_pix | точка за такт: s, t шагом, волна, адрес плитки, кэш текстур 8 КБ (2 пути, строка 64 байта), lightmap (кэш клеток), билинейный свет, colormap, прозрачность (кэш alphamap) | ~3500 LUT, ~16 BSRAM, 3 DSP |
| bz_out | сборка куска цвета 16 байт, запись пачкой с маской (у прозрачных — после чтения куска) | ~500 LUT |
| bz_2d | POINT, PIC, FILL — через тот же путь записи | ~600 LUT |

Сверка: тот же стенд (трасса Quake 2, вся память против модели после каждого кадра) — сначала с
идеальной памятью, затем с моделью SDRAM, у которой реальные задержки моста.

## Этап B: растеризатор готов первым (23.11.2026)

`bz_raster.sv` — многоугольник → поток точек (x, y, zi, s, t, l), без памяти. Три ступени одновременно:
рёбра (DDA, строка за такт, по два делителя на цепочку), куски (4 делителя перспективы `bz_div4`,
очередь заданий, приём по порядку за 3 такта на кусок), точки (приращения). Два банка градиентов —
следующий многоугольник начинается, пока доделывается прежний.

Проверка — `tb/tb_raster.cpp` (`tb/run_raster_sim.sh`): модель через крючки (`bz_set_hooks`) отдаёт каждый
многоугольник растеризатора (POLY и TRIS после постановки) и его точки; RTL получает те же многоугольники
потоком, точки сверяются по одной до бита, выход случайно придерживается (рукопожатие).

| Версия | Тактов на точку | Что изменилось |
|---|---|---|
| v1 | 8,31 | всё по очереди, делитель по биту (48 тактов) |
| v1 + bz_div4 | 2,89 | radix-4, без пустых шагов: в среднем 8 тактов на деление |
| v2 | 1,44 | строка за такт, два банка, 2 делителя перспективы, очередь заданий |
| v3 | 1,22 | 4 делителя перспективы, по 2 на цепочку рёбер, приём за 3 такта, 2 места кусков |
| v4 | 1,35 | меньше логики: делители с фиксированной длиной частного (bz_div4 FIXQ, без сдвигателя), по одному на цепочку, градиенты — раздельные C/A/B |
| v5 | 1,39 | тайминг: кусок на стороне I — 3 такта, начало ребра — множители, N, модуль по тактам; края отрезка в 16 битах |

На трассе (300 кадров, 224 тыс. многоугольников, 30 млн точек) — совпадение до бита у всех версий;
v1 — на всей трассе (2017 кадров, 325 млн точек) с задержками выхода. Худший кадр 424×240 (308 тыс.
точек) у v3 — ~6 мс на 60,75 МГц, у v5 — ~7 мс.

Пробная сборка Gowin одного растеризатора (`synth/build_raster.sh`, обёртка `synth/bz_raster_wrap.sv`: входы из
сдвигового регистра, выходы — XOR в один вывод):

| | Логика (с обёрткой) | clk_mem |
|---|---|---|
| v3 | ~11 тыс. (9 тыс. LUT + 2 тыс. ALU) | — (ошибка в .sdc обёртки) |
| v4 | 8170 (40 %) | 51,4 МГц — мало |
| v5 | 7812 (38 %), из них ~1000 триггеров — регистр обёртки | **60,87 МГц** (нужно 60,75), нарушений нет |

Растеризатор — ~6,8 тыс. логики: вместе с оболочкой (5,3 тыс.) это ~58 % кристалла, на конвейер точки
остаётся ~8,5 тыс. Где ещё ужать: очередь заданий (4 × ~230 бит) и очередь кусков (2 × ~300 бит) — в
распределённую память вместо триггеров и мультиплексоров; v1 = v0 + A·n — четыре умножения 32×5 в LUT
(можно одним умножителем на 4 такта: у стороны I есть запас).

Дальше — точки: z, тексель, свет, запись (bz_pix и клиенты SDRAM).

## Этап B: ядро, конвейер точки, шесть клиентов SDRAM (23.11.2026)

Всё рисование — `bz_gpu.sv` (в оболочке `bz_top.sv` вместо ядра этапа A; этап A — ключ `-StageA`):

```
команды → bz_core2 ──POLY, TRIS (после постановки)──► bz_raster ──точки──┐
             │  FILL, POINT, PIC: точки прямоугольника — само ядро ─────────┴─► bz_pix (6 ступеней) ─► SDRAM
             └─ WRITE, таблицы SETUP — bz_memif
```

- **bz_pix** (`bz_pix.sv`) — шесть ступеней, общий «стоп» при промахе: A вход (волна, z в 16 бит, y·S + x,
  клетка lightmap), B (волна, координаты текселя, четыре клетки lightmap из BSRAM), C (адрес текселя, кэш
  текстур, свет по колонке), D (попадание, строка света), E (кусок z: тест и запись; ключ; colormap),
  F (кусок цвета, прозрачность). Записи z и цвета — только в такт, когда точка уходит дальше.
- **Куски** z (16 значений) и цвета (32 точки) — регистр на пачку SDRAM 32 байта с маской «записано»;
  вытесненный кусок — в буфер записи, мост заберёт его слова потом. Читать пачку нужно, только если
  точке нужно старое значение (z-тест, прозрачность): заливка z и обычный цвет только пишут.
- **Кэши**: текстуры 8 КБ (2 пути, строка 32 байта, метки в BSRAM, сброс — 128 тактов), alphamap 2 КБ
  (прямое отображение). **Lightmap** — не кэш: ядро грузит его целиком (до 64×64) в один из двух слотов
  (4 банка BSRAM по чётности строки и колонки: четыре клетки за такт), пока точки читают другой слот.
- **Банки состояния**: режим, текстура, lightmap, фаза — в двух банках; точки несут номер банка,
  растеризатор выдаёт метку конца многоугольника (`out_end`), по её выходу из F банк свободен.
- **bz_core2** (`bz_core2.sv`): разбор команд как у этапа A; многоугольник — в растеризатор с банком;
  FILL/POINT/PIC — само перебирает точки (режимы SOLID, ZRAW, NOCOL конвейера); буферы вершин моделей —
  BSRAM (вершины треугольника читаются по одной за такт), делитель постановки — `bz_div4` FIXQ=48.
  Слив (растеризатор и конвейер пусты, куски — в SDRAM) — только перед WRITE, SETUP и FRAME; после
  WRITE/SETUP перед первой точкой — «забор»: чтение мимо кэша memif (ответ — после всех записей ядра,
  мост держит порядок одной метки) и сброс кэшей конвейера.
- **Метки моста**: 100 тексели (своя быстрая очередь моста), 001 z, 011 цвет, 101 alphamap, 111 lightmap,
  010 ядро; приоритет в этом порядке; у оболочки старше — 000 вывод и 110 Evo.

Стенд — `tb/tb_gpu.cpp` (`tb/run_gpu_sim.sh`): `bz_gpu` + настоящий мост `sd_bridge` + модель контроллера
SDRAM на C++ (случайные задержки, регенерация), после каждого кадра вся память против C-модели.

Первый прогон (300 кадров трассы t169, 30,2 млн точек растра): **память RTL = память модели** после каждого
кадра. Время — 11,6 мс на кадр в среднем на 60,75 МГц, тяжёлые кадры ~20 мс; 7,0 такта на точку растра
(всё вместе: заливка z 95 тыс. точек на кадр, картинки, слив). «Стоп» конвейера на точку растра: кусок z —

## Ядро 0.03: FIFO_FREE в коде Грея и тайминг (24.11.2026)

- **Почему.** На плате (ESP 0.1.167) LINK вернул FIFO_FREE = 0x858 при очереди в 2048 слов. 0x0C отдавал
  комбинационный выход вычитателя `bz_fifo` (домен clk_mem), а `fb_link` защёлкивает слово по фронту link_sck
  без синхронизации — захват посреди смены счётчика даёт смесь битов. Прошлый сбой на плате (STATUS 0x37:
  переполнение очереди и неизвестная команда, сдвиг потока) — такое же чтение, принятое за место.
- **FREE_GRAY, LINK 0x1C** = `{0x47, 12'd0, Грей(FIFO_FREE)}` из регистра clk_mem. Код Грея годится, потому что
  FIFO_FREE за такт меняется не больше чем на 1 (push −1; pop без подгрузки +1; подгрузка выхода — 0); захват
  по SCK даёт старое или новое число. Q2.ELF при VERSION ≥ 0.03 читает 0x1C, проверяет метку и нули.
- **FIFO_FREE снизу — ноль.** Стенд нашёл: запись сверх места заполняет память целиком при занятом выходном
  слове, `DEPTH − used − q_valid` = −1 = 0xFFF. Теперь free считается от числа слов (used + q_valid) с
  насыщением — монотонно, ±1 за такт.
- **Тайминг.** Первая сборка 0.03 (+23 LUT, +23 триггера) не прошла: clk_mem 60,0 МГц — путь «метки кэша
  текстур (BSRAM без выходного регистра) → сравнение 11 бит → st_d → adv → разрешение записи куска цвета c_d»
  (13 уровней, −0,202 нс); clk_sd 119,4 — мост c_req → разрешение выводных регистров адреса SDRAM. Правка:
  ступень F пишет точку один раз, как только сама готова (`f_wr = f_cneed && !st_f && !f_done`), а не в такт
  adv; f_done держит «уже записано», пока точка ждёт общий шаг. Сборка b не развелась (35 цепей, CLS 96 %),
  сборка c — без двоичного регистра под 0x0C — сошлась: clk_mem +0,223 нс, clk_sd +0,101, точка +1,403,
  hold +0,074. Тактов на кадр на стенде — столько же, сколько у 0.02.
- **Следующий кандидат** — тот же путь в ступени E: метки кэша → adv → запись куска z (z_d, +0,49 нс у
  сборки c). Чинится так же (запись z один раз по готовности ступени E).
- Выпуск: `release/0.03` (Q2.BIN ae764a…).
